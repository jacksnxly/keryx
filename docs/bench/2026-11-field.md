# keryx on real work: 71 runs against the workflow it replaced

How keryx did on the owner's real work in its first week, scored against the tasks done in the month before with the setup it replaced. This is field data, not a controlled benchmark: different tasks, one owner, scored after the fact from the session transcripts. The tasks are private work, so only aggregates are published here.

## What was compared

- **keryx 1.0–1.3**: every run from 25 October to 1 November 2026. 71 runs in 6 projects: 42 features, 14 bugs, 7 migrations and 8 others; 6 small, 31 medium, 34 large.
- **Before**: every task from 22 September to 25 October 2026 that a popular third-party skill pack drove. That pack brainstorms, writes a plan, hands each task to a subagent and finishes the branch. 47 tasks in 10 projects: 33 features, 9 bugs and 5 others; 7 small, 16 medium, 24 large.
- Five projects appear in both. One task that used both workflows is left out.
- Both used the same coordinator model (Claude Opus 5.5 wrote nearly all coordinator tokens) and the same owner.
- A "project" here is one Claude Code project folder.

## How it was scored

Everything came from Claude Code's own session transcripts. Each session became a digest:

- the owner's prompts, and the agent's last words before each one;
- skill calls, questions and answers, and interruptions;
- pull requests, and keryx's run-log milestones.

Secrets were removed, and the two workflows were renamed to neutral codes. Six judge subagents then scored every run on one rubric, with a timestamped quote for every deduction:

| Part | Points | Rule |
|---|---|---|
| Delivered | 30 | 30 if shipped as asked, within the autonomy given; 20 with gaps the agent named itself; 10 if partly done; 0 if nothing shipped |
| Correct at done | 30 | −10 for every "done", "fixed", "live" or "all tests pass" later found untrue |
| Owner effort | 25 | −5 per correction or redirect; −2 per nudge to a stalled run or per avoidable question |
| Verified | 15 | 15 if checked on the real surface plus a review or a test shown to fail first; 10 for tests or CI; 5 if little was shown |

A false done counts only for a claim about delivered work; a plan or spec corrected before the build is part of planning. Applying that rule the same way across all judges raised three of the earlier tasks and changed no keryx run.

## Results

| | keryx | before |
|---|---|---|
| Runs | 71 | 47 |
| Score, mean (median) | **90.9** (95) | 83.3 (88) |
| Runs scoring 90 or more | 72 % | 47 % |
| Runs with a false "done" | **11 %** (8) | 36 % (17) |
| False "done" claims per run | 0.18 | 0.55 |
| Owner corrections per run | **0.15** | 0.64 |
| Nudges to a stalled run, per run | 0.06 | 0.23 |

- **Overall**: the mean score differs by **+7.6 points**, with a 95 % bootstrap interval of +3.3 to +12.2. Leaving out the verification part, the other three parts together still differ by +7.6.
- **Runs still in progress**: leaving out the 11 runs that had not finished, keryx scores 91.8 and the earlier workflow 84.7.
- **By size**: small tasks tie (95.8 against 95.7). Medium tasks gain 4 points (92.5 against 88.5). Large tasks gain 12 points (88.5 against 76.2). Most of the gain is on work that is split into slices.

Rough figures, measured over each run's time window, are shown below. Tasks of the earlier workflow often ran for days, and their windows include unrelated work from the same session, so these figures overstate the earlier workflow's side:

| Median per run | keryx | before |
|---|---|---|
| Busy time (silences over 10 minutes left out) | 126 min | 202 min |
| Claude spend at API list prices | 0.54× | 1× |

Claude spend counts Claude tokens only, at list prices: Opus 5.5 at $4 input, $20 output and $0.20 cache reads per million tokens, with cache writes at 1.25× input. keryx's GLM and Cursor executors run on flat-rate plans and are not counted.

## What did not improve

- **Verification.** The verified part scored the same in both, 11.9 of 15. Judges saw checks named in both workflows' reports, and the digests cut long reports short.
- **Every project.** In one of the five shared projects the two scored about the same (91 against 90).
- **Large builds.** keryx's four lowest finished runs, scoring 56 to 70, were large builds where the owner or a later review found parity gaps or UI bugs after "done". The earlier workflow failed the same way, more often.

## Limits

- **Observational.** The tasks and the weeks differ, and the owner may have got better at briefing over time; the two can't be separated. The earlier workflow drifted little: its tasks scored 82.4 before 15 October and 84.1 after.
- **Not blind.** keryx runs are recognisable by their run logs.
- **One judge per run.** Two judges scored the same 8 runs: 7 were within 5 points, with a mean difference of 4.4. A single disputed false done moves a run by 10 points.
- **Narrow sample.** One owner and 11 projects, mostly feature work.

Per-run scores, judge evidence and the digests are kept privately with the owner's other field data (see `docs/field.md`).
